## Flujo completo

1. Al abrir login, el constructor lee `workshop_preferences`, intenta parsearlo y lo mezcla con preferencias por defecto. Si falla, registra el error y continúa. Evidencia: [src/app/login/login.component.ts:20](../src/app/login/login.component.ts#L20), [src/app/login/login.component.ts:22](../src/app/login/login.component.ts#L22).
2. El botón llama a `login()`. Se rechazan usuario o contraseña nulos, indefinidos o vacíos al aplicar `trim()` para la comprobación; los valores enviados no se normalizan. Durante la petición se activa `busy` y el botón queda deshabilitado. Evidencia: [src/app/login/login.component.ts:33](../src/app/login/login.component.ts#L33), [src/app/login/login.component.ts:39](../src/app/login/login.component.ts#L39), [src/app/login/login.component.html:34](../src/app/login/login.component.html#L34).
3. Si la respuesta contiene un token evaluado como verdadero, se guardan `workshop_token`, `workshop_user` serializado y `workshop_preferences` serializadas en `localStorage`; después se navega a `/dashboard`. El `finally` restablece `busy` tanto en éxito como en error. Evidencia: [src/app/login/login.component.ts:46](../src/app/login/login.component.ts#L46), [src/app/login/login.component.ts:58](../src/app/login/login.component.ts#L58).
4. Al iniciar dashboard, se lee el token y se parsea el usuario. Si el parseo termina y no hay token, se navega a `/login` sin consultar tareas. El parseo de usuario está antes del `try` de la consulta; un JSON inválido no sigue ese manejo de errores. Evidencia: [src/app/dashboard/dashboard.component.ts:36](../src/app/dashboard/dashboard.component.ts#L36), [src/app/dashboard/dashboard.component.ts:37](../src/app/dashboard/dashboard.component.ts#L37), [src/app/dashboard/dashboard.component.ts:42](../src/app/dashboard/dashboard.component.ts#L42).
5. Con token presente, se consulta `/api/tasks` con propietario y Bearer. Se conserva el arreglo en `tasks`, se excluye de `visibleTasks` solo el estado exactamente igual a `ARCHIVED` y se agrega `label` a las tareas visibles mediante `formatTaskLabel`. El comparador de prioridad devuelve `-1` si `a.priority > b.priority` y `1` en los demás casos; no se infiere un orden de negocio de prioridades. Evidencia: [src/app/dashboard/dashboard.component.ts:43](../src/app/dashboard/dashboard.component.ts#L43), [src/app/dashboard/dashboard.component.ts:48](../src/app/dashboard/dashboard.component.ts#L48), [src/app/dashboard/dashboard.component.ts:54](../src/app/dashboard/dashboard.component.ts#L54).
6. La actualización de tareas o error se ejecuta dentro de `NgZone.run` y llama a `detectChanges()`. La plantilla muestra carga, error, tareas o estado vacío; el saludo usa `displayName` o `username`. Los estados se traducen mediante `STATUS_LABELS`. Evidencia: [src/app/dashboard/dashboard.component.ts:7](../src/app/dashboard/dashboard.component.ts#L7), [src/app/dashboard/dashboard.component.ts:59](../src/app/dashboard/dashboard.component.ts#L59), [src/app/dashboard/dashboard.component.ts:66](../src/app/dashboard/dashboard.component.ts#L66), [src/app/dashboard/dashboard.component.html:6](../src/app/dashboard/dashboard.component.html#L6), [src/app/dashboard/dashboard.component.html:13](../src/app/dashboard/dashboard.component.html#L13).
7. «Cerrar sesión» invoca `logout()`, elimina token y usuario locales y vuelve a `/login`. Las preferencias sobreviven. Evidencia: [src/app/dashboard/dashboard.component.html:9](../src/app/dashboard/dashboard.component.html#L9), [src/app/dashboard/dashboard.component.ts:74](../src/app/dashboard/dashboard.component.ts#L74).

## Límites de lo confirmado

El código consumidor no permite confirmar códigos HTTP concretos, estructura completa de usuarios o tareas, formato/expiración del token, autorización por `owner`, política CORS ni revocación remota. Esas comprobaciones requieren coordinar los servicios externos sin ampliar el ámbito de edición. No se añadieron endpoints ni se cambió el flujo funcional.
